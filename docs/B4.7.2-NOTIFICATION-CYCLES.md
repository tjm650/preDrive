## Delivery semantics

- Initial alert deliveries use sequence 1.
- Repeated alert deliveries use sequence 2 onward, with a five-minute next-escalation interval.
- Push deliveries are unique by recipient, device token and sequence; email deliveries are unique by recipient and sequence.
- Each active Expo device receives its own push delivery record. Deleting a device token preserves the delivery row and its school ID while clearing the device reference.
- Expo ticket IDs are stored as provider message IDs. Receipt status is tracked separately; a ticket only confirms Expo accepted the message, not that APNs/FCM accepted it.
- The escalation RPC is executable only by `service_role`; it locks due alerts with `FOR UPDATE SKIP LOCKED`, queues only unacknowledged recipients with active memberships, and advances the next escalation by five minutes.
- Repeats stop when the alert is closed, repetition is disabled, no unacknowledged recipient remains, or the safety cap is reached.

## Remaining worker work

The delivery worker must now use the delivery row's `device_token_id` rather than selecting one most-recent device. It must safely suppress push rows whose referenced token has been revoked/deleted. It must poll Expo receipts using the stored ticket IDs after the recommended delay, update receipt state without resending already-sent messages, and revoke a device token on a receipt-level `DeviceNotRegistered` response. Receipt errors must remain distinct from send attempts.
